# 报名奖励清单弹层增强 — 设计

日期：2026-08-30
页面：`https://v.joho.cn/#/pages/activity/detail?id=...`
文件：C 端 `e:\code\shao\pages\activity\detail.vue`；后端 `e:\code\basic\plugins\zhao-point\server\src\services\activity.ts`

## 背景与目标

报名时弹出的「报名奖励」清单弹层（`reward-preview-panel`，分必得区/解锁区）部分元素不可见或样式欠佳：

- 获得积分值看不见
- 锁头看不见、解锁状态（去解锁/已解锁）看不清
- 解锁条件看不见
- 解锁通道看不见
- 整体样式不美观

目标：让①积分值②锁头③解锁状态④解锁条件⑤解锁通道全部清晰可见，弹层更美观，权益多时可滚动（滚动已具备）。

## 根因分析（最小改动，只做实现）

| 现象 | 根因 |
|---|---|
| 积分值看不见 | 后端 `unlockCheck().rewards[]` 每个条目**只返回** `{ id, name, type, mode, condition, unlocked }`，**没有 `points`**。前端 `v-if="r.points"` 恒为假 |
| 解锁通道看不见 | 后端已返回 `channel`，但前端**没有渲染「解锁通道」元素** |
| 锁头/解锁状态不清 | 模板仅一个 `🔒` emoji（跨端渲染不稳定），无「去解锁/已解锁」显式状态徽标 |
| 解锁条件不清 | 条件文字存在但样式拥挤（字号 22rpx、灰、flex-shrink:0），且与积分/状态挤在一起 |
| 样式不美观 | 分区/条件/积分排版松散 |

## 改动方案

### 1. 后端 `activity.ts` — unlockCheck 增补 `points`（仅展示，非发分依据）

- `resolveCondition(r)` 分支构造 reward 条目时，为 `type === 'points'` 的条目补 `points: r.amount`，其余 `points: 0`。
- 保留现有 `id/name/type/mode/condition/unlocked` 与 `channel` 返回结构不变。
- 不触碰 `signup` 发分逻辑、不做数据模型改动。

### 2. C 端 `detail.vue` — reward-preview-panel 模板与样式增强

- 顶部新增「解锁通道」提示条：`解锁通道：{{ rewardPreviewData.channel?.label || '完成解锁通道' }}`（channel 已由 unlockCheck 返回）。
- 解锁区每行强化状态表达：
  - 锁头：解锁状态行首用图形化锁头（锁定 🔒 / 已解锁 ✓），并配「去解锁 / 已解锁」项目符号呈现，替代单一 emoji。
  - 解锁条件：独立、可换行的条件文本（`rewardCondText(r)`），赋予更高的对比色与内边距。
  - 积分值：`reward-preview-val` 橙色强调，确保 `v-if="r.points"` 命中后有值（依赖后端补 points）。
- 样式美化：
  - 必得区/解锁区卡片化，间距统一；
  - 积分值颜色（橙）与文字层级清晰；
  - 弹层高度沿用 `.signup-panel` 的 `max-height:78vh; overflow-y:auto`（已具备），仅校正 `reward-preview-panel` 的 padding，避免滚动时底部按钮被遮挡错乱。

## 约束

- `points` 仅用于弹层展示，**不参与**发分判定；`unlocked` 严格采用后端返回（含 selectMode 池化口径），前端不做二次判断，保证「展示」与「实际发分」一致。
- 不改数据模型、不改 `signup` 发分逻辑、不改 `web` 运营端。
- 遵循 shao 目录铁律：不升级 vue、不新增依赖。

## 风险点

- `points` 字段新增属后端返回体扩展，旧部署与该前端包兼容（前端缺失时以 0 兜底显示「必得分」区域仍在）；前后端需**同步发布**，避免新增前端读取到旧后端无 `points` 导致积分值仍空。
- `rewardCondText` 对未知 condition 返回空串：新增 condition 时需同步扩充映射，否则条件不显示。

## 验收

报名时弹层可见：必得分/解锁分、锁头🔒/已解锁✓、去解锁/已解锁状态、解锁条件文字、解锁通道名；权益条目多时面板内滚动；弹层整体美观统一。
